1. Desktop: the org name becomes the switcher

Priya is owner of Acme Studio and a member of Northwind Bakery. She asked to join Himalayan Ritual and is waiting. The logo and name at the top of the sidebar become one button. It opens a small menu right under it.

Desktop · 1440 · menu open, keyboard focus on Northwind Bakery

Decisions

  1. The button keeps today's look: amber initial, name, 44px tall. It gains a quiet up-down chevron and a hover fill. Nothing else in the sidebar moves.
  2. The menu opens under the button, 300px wide, so long names have room. It overlaps the page a little, like any menu.
  3. Each row: initial, name, your role in that org. A tick (in --link, since amber is too faint for an icon on white) marks where you are.
  4. Active orgs are listed A to Z, not by last use, so they never jump around.
  5. Pending requests sit under a hairline: grey initial, grey name, a clock and "Waiting for approval". They do nothing when clicked.
  6. Declined and removed memberships are not listed. There is nothing you can do with them.
  7. Picking an org posts to /orgs/{id}/switch. Picking the one you are in just closes the menu.
  8. No create or join rows yet. See section 7.

ARIA: the button has aria-haspopup="menu" and aria-expanded. The list is role="menu" labelled "Your organisations". Active orgs are menuitemradio with aria-checked. Pending rows are menuitem with aria-disabled="true". They stay focusable, so a screen reader hears "Himalayan Ritual, waiting for approval, unavailable".

Build note: one <form method="post"> around the menu, and each row a <button formaction="/orgs/31/switch">. It works without JavaScript. JavaScript adds the arrow keys and the loading state.

2. Phone: tap the org name on Home

Home's header already shows the org name on phones. It becomes a button with a small chevron, and opens a bottom sheet. More gets the same entry as its first row, so you can switch without going back to Home.

Decisions

  1. Home's header, because that is where the name already is on a phone. It stays where your thumb expects it. No new header on every tab.
  2. More gets one row at the top: initial, name, role, "Switch". It opens the same sheet. People who look for settings find it there.
  3. The sheet is the app's existing dialog.sheet: handle, title "Your organisations", a 44px close button. Rows are 60px, bigger than desktop, for thumbs.
  4. Tapping a row shows a spinner and "Switching…" on that row. The other rows dim and do nothing. Then the whole page loads fresh on Home.
  5. The sheet closes on a backdrop tap, a swipe down, the close button or Esc, as the other sheets do.
  6. With one org, the header stays plain text and More shows no row, exactly as today.

3. After a switch

You land on Home in the new org. A toast says where you are, then fades after 3.5 seconds like every other toast. The sidebar, the header and every count are now Northwind Bakery's.

Phone · Home in Northwind Bakery

Decisions

  1. Copy: "You're now in Northwind Bakery". Plain, from Priya's side. No "Switched organisation successfully".
  2. A normal toast (the dark one), not the green success one. It is information, not an achievement.
  3. Toast placement as today: above the tab bar on phones, bottom right on desktop.
  4. How it gets there: the switch redirects to /dashboard?switched=1. Home renders the existing flash with the org it actually resolved, so a hand-made link can only ever state the truth. app.ts then removes ?switched=1 with history.replaceState, so a reload does not repeat it. This is the same pattern as /more?signed_out=1.
  5. Errors stay in the menu or sheet (section 6): a toast, and the list stays open.

The notice

  1. A card at the top of the page, not a toast. It must not vanish before it is read, and it can hold a draft.
  2. Title, always: "This tab was showing Acme Studio. You're now in Northwind Bakery."
  3. Why, in one line: "You switched organisation in another tab, and every tab follows."
  4. "Back to Acme Studio" switches the browser back. "Dismiss" (the X) closes it. It also goes away on the next page.
  5. role="status", so a screen reader announces it. It does not take focus.
  6. The tab opened by the switch itself shows the toast from section 3, never this notice.
Question for Raj: where the stale tab landsHome in the new org (recommended). The plan says HX-Refresh, which reloads the same address. On an address with an id from the old org, like /tasks/58 or /chat/12, that reload is a 404 page in the new org. Sending HX-Redirect: /dashboard instead matches what a switch does, and always lands somewhere that works.
Question for Raj: offer "Back to Acme Studio"?Recommended yes. It is what Priya wanted in this tab. The cost: tab B now becomes the stale one and gets the same notice next time it loads anything.

Superseded after review (19 October). Drafts are not copied into sessionStorage. When a tab holding typed text or an upload is refused, it does not move: the text stays in the form and one banner appears in place, with "Back to Acme Studio" and "Go to Home". See docs/plans/multi-org-3.md, "The typed-text guard".

Can the draft be kept? Yes, the text, in this tab.

What is feasible in PR 3, all in frontend/app.ts with no server change:

  • Catch it before the page moves. HTMX fires htmx:beforeOnLoad before it acts on HX-Redirect. On a 409, copy every filled text field on the page into sessionStorage: its label and its value. Plain (non-HTMX) forms are copied in the same submit listener that adds the hidden _org field.
  • Show it after. The new page reads it, shows it in the notice with "Copy text", then deletes it. Session storage is per tab and gone when the tab closes.
  • Only text. Task title and description, notes, meeting notes, chat messages, comments.
  • Never passwords or logins. Skip type="password" and any form marked data-no-draft (the logins and unlock forms). They must not sit in browser storage in plain text.
  • Not files. A browser cannot put a file back into a file field. The notice names the file so Priya knows to upload it again.

Not in PR 3: putting the draft back into the form by itself after switching back. It needs the old address and a match on form and org. Possible later.

Unverified: the order of htmx:beforeOnLoad and the HX-Redirect handling in the vendored HTMX build. The engineer should check it before relying on it.

Question for Raj: draftsKeep text to copy, in this tab only (recommended for PR 3). Or drop drafts and only show the notice, which is less work but loses what was typed when the 60-second check fires mid-sentence.

5. Super admin acting in an org

Raj is super admin, owner of Zen Scale, and has entered Acme Studio from /admin. The banner exists today and does not change: "You are inside Acme Studio as platform admin. Changes you make are real." with Leave.

Desktop · 1440 · acting in Acme Studio, menu open
Phone · acting, sheet open

Decisions

  1. The button shows the acting org with a second line: a shield and "Platform admin". So the sidebar says it too, not only the banner.
  2. The menu splits in two. "Acting in": Acme Studio, ticked, role "Platform admin". Then "Your organisations": the orgs Raj really belongs to.
  3. Picking one of your own orgs switches to it and ends acting, as the endpoint already does. The note under the list says so: "Switching ends acting in Acme Studio."
  4. Leave stays in the banner only. One way out, in one place.
  5. No list of every org in the menu. Entering another org stays on /admin, which already lists them.
  6. A super admin acting with no membership of their own has nothing to switch to, so the button is plain, as in the single-org case.
  7. Acting in an org you also belong to: it shows once under "Acting in". Your own row for it stays under "Your organisations" without a tick. Picking it drops acting and gives you your real role there.

7. Room for PR 4 and PR 6

PR 4 adds "create another organisation" and PR 6 "join with an existing account". The recommendation is to show neither until it works.

Recommendation: do not show them yet

  1. A greyed "Coming soon" row is a promise the app cannot keep, sitting in a menu people open every day.
  2. Nobody sees the menu before PR 4 anyway, because nobody has two orgs. A stub would only reach the switcher's first users once PR 4 is out, by which time "create" is real.
  3. The room is already there. The menu ends with the list, so PR 4 adds a hairline and one row under it ("New organisation", plus icon), and PR 6 a second ("Join with a link"). The phone sheet gets the same two rows. Nothing in this design has to move.
  4. One consequence to accept: with the stubs hidden, a one-org person has no way to reach "create" from the switcher. PR 4 will need the switcher to show for one org too, as a menu with your org plus "New organisation". That is PR 4's design call.
Not drawn on purpose. Per the design rules, features outside PR 3 are listed here, not shown in the screens.

8. Questions for Raj

Each with a recommendation.

  1. One org: no dropdown affordance at all. Recommend: yes, plain name as today.
  2. PR 4 and PR 6 entry points: hide until built, or show disabled stubs. Recommend: hide.
  3. Phone placement: Home header plus a row on More, or More only. Recommend: both.
  4. Where a stale tab lands: Home in the new org (HX-Redirect: /dashboard), or reload the same address (HX-Refresh, as the plan says). Recommend: Home. Reloading an id page from the old org gives a 404. This changes the plan's wording.
  5. Drafts in a stale tab: keep text to copy, in this tab only, never passwords or files. Recommend: yes for PR 3. Restoring into the form after switching back can come later.
  6. "Back to Acme Studio" in the notice: recommend offering it, knowing the other tab then becomes stale.
  7. Unread dots for other orgs. The multi-org-2 plan lists them under PR 3's scope. This brief does not, so they are not drawn. Recommend: leave them for a later PR. They need a count per org for every page load, and a dot on the button would need explaining.
  8. Order: A to Z with pending at the end. Recommend: yes, over most recently used, so rows never move.
  9. Declined and removed memberships: not listed. Recommend: yes. They can't be acted on, and listing "Removed" in a menu is unkind.
